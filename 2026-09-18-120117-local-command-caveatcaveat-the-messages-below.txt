  all four are equivalent right now.

  Use https:// explicitly and don't try http://localhost:8080 — that's the HSTS
  trap from the verification report; the browser upgrades it to TLS against a
  plaintext listener and you get ERR_SSL_PROTOCOL_ERROR. 8080 is for probes and
  curl only.

  What's there

  Sign-in lands you on the dashboard inside the app shell. The screens are:

  - Dashboard (/)
  - My tasks (/tasks) and Unassigned queue (/tasks/unassigned), with detail at
    /tasks/:id
  - Teams (/teams, /teams/:id)
  - Projects (/projects, /projects/:id)

  The database is empty. The only migration is V1__baseline.sql — schema, no
  seed rows. So the dashboard and every list will be blank on first login, which
  is correct behaviour, not a broken deploy. Work from the outside in: create a
  team, then a project under it, then tasks.

  Other ways in

  - Identity provider admin — https://localhost:8444/idp/admin, realm hive.
    Admin credentials come from your containers/.env.
  - API directly — https://localhost:8444/api/v1. It returns 401 without a
    bearer token (just confirmed). Grab one via the realm's token endpoint at
    /idp/realms/hive/protocol/openid-connect/token using the public hive-web
    client.
  - No containers — npm start in frontend/ serves on http://localhost:4200,
    where devAuth is on and the app mints a local token from POST 
    /api/v1/dev/token instead of doing a real OIDC round trip. That endpoint is
    @Profile("dev") and doesn't exist in prod. Note 4200 is registered as a
    redirect URI in the realm too, if you'd rather use the real IdP there.

  A real authorization-code + PKCE login was verified on 2026-09-15, but with

  end-to-end test. So the protocol and the token are proven; the sign-in

  untested gap rather than something you're doing wrong. Happy to drive it

  What went wrong

  Your click never reached a login form. The authorize endpoint rejected the
  request and bounced straight back to the callback:

  Location: .../auth/callback?error=invalid_scope

  &error_description=Invalid+scopes%3A+openid+profile+email+offline_access

  The SPA asked for openid profile email offline_access. The hive-web client in
  the realm declares only defaultClientScopes and no optional ones — I confirmed
  against the live Keycloak that its optional scope list is genuinely empty, so
  offline_access isn't assignable. An issuer refuses the whole request over one
  unknown scope rather than quietly dropping it, which is why you got an error
  page instead of a degraded login.

  The fix, and why this one rather than the other

  Two options: grant offline_access on the client, or stop asking for it. I
  removed it — the code comment in app-config.ts claiming offline_access "is
  what produces a refresh token" was simply wrong, and I checked rather than
  assumed. A full PKCE flow with openid profile email returns:

  granted scope : openid profile email
  refresh_token : yes          (refresh_expires_in: 1800s)

  Keycloak issues a refresh token from the ordinary code flow regardless;
  offline_access only asks that it outlive the SSO session. That's worthless
  here, because the token set lives in sessionStorage (browser.ts:73) and dies
  with the tab — so it would have been a longer-lived credential in a public
  browser client for no benefit.

  Changed: both environment files, the misleading doc comment, and a stale
  comment in auth-service.ts. The test at app-config.spec.ts asserted 
  offline_access was present — it encoded the same wrong belief, so it now
  asserts the absence with the reason. 471/471 frontend tests pass; image
  rebuilt and the service recreated.

  The realm fix turned up a second defect

  I expected to remove one inert line. openid was indeed discarded silently at
  import — Keycloak has no client scope by that name; it's an OIDC request
  value. But spelling out defaultClientScopes by hand had also dropped basic,
  and basic is what puts sub in a token.

  Every access token this realm minted had no subject claim. Nothing failed,
  because CurrentUser.kt:98 does subject = jwt.subject ?: email — a fallback
  written so a token without a usable subject still resolves. So a
  non-conformant token was being carried by a fallback meant for something else.
  The client now holds basic and acr among its defaults plus the standard
  optional set — what Keycloak would have created had the list never been
  overridden.
